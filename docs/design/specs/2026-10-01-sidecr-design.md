# Sidecr: design

Status: draft for review, 2026-10-01 (first called herdr-pal; renamed Sidecr on 2026-10-02, the names below are the current ones)
Authors: the maintainer, with Claude

> The original design, kept as a record. Several first-version limits here (two exchanges, no history, no native window) were lifted later; the README and `docs/` describe what the code does today.

## 1. Purpose

Sidecr is a small companion window for the [herdr](https://github.com/herdrdev/herdr) terminal multiplexer. It does not replace herdr or its terminal. It adds what a terminal cannot do well for an agent conversation: attach files with a paperclip or by paste/drag, see image previews, and click links and file paths.

One keystroke, while you are in a herdr pane running Claude Code, opens a window bound to that same pane. You see the last couple of exchanges, attach something, send, close the window, and you are back in the terminal. The session never moved.

### Alternatives considered

A complete replacement client (its own sidebar, its own terminal, remote access, authentication, push) is a different, larger scope. Sidecr keeps herdr's own terminal and layout untouched and builds only the chat-and-attachments layer on top of them.

## 2. Success criteria

1. From a herdr pane running Claude Code, a single key opens the window on that pane in under two seconds.
2. The window shows the last two user/assistant exchanges of that pane's Claude session, updating live while Claude writes.
3. Pasting a screenshot (or dragging a file, or using the paperclip) and sending arrives in the same Claude session, and Claude reads the image.
4. URLs and file paths in the shown messages are clickable: URLs open in the default browser, image files preview in the window, other files open with the system default.
5. Works on Windows and Linux.
6. Closing the window leaves the herdr session exactly as it was.
7. Inside the window, a quick switcher (a command-palette gesture) moves the window from one agent pane to another by name, without going through herdr's prefix search.

## 3. Non-goals (first version)

- Agents other than Claude Code.
- A dashboard of several panes; one pane per window.
- Approval or question cards; the terminal handles prompts.
- Remote machines, auth, push notifications. (The window's own local notification when Claude finishes or needs you, shown by the browser while the window is in the background, is not push: nothing is sent from outside the machine.)
- Long history or search; "last two exchanges" is the unit.
- Rendering the terminal.
- A native executable (a Tauri shell is a possible later step, see section 10).

## 4. Architecture

Three parts, one purpose each.

**4.1 herdr plugin (entry)**
A herdr plugin (`herdr-plugin.toml`) declares an action `open`, with `platforms = ["linux", "windows"]`. The user binds a key to it in herdr's `config.toml`:

```toml
[[keys.command]]
key = "alt+s"
type = "plugin_action"
command = "<plugin-id>.open"
description = "sidecr"
```

`alt+s` is the single chord, and it both opens and closes the window (see the toggle below; inside the window `Alt+S` closes it too, section 4.4). Task 0 verified on Windows that a chord of this kind reaches herdr from the user's terminal, including while a Claude Code pane has focus, and that the action runs with the right pane (checked with `ctrl+shift+j`, which also arrived, as did `alt+j`; `ctrl+alt+j` did not). The chord is bound in the user's own `config.toml`, so it can be changed there if another tool takes it.

The action runs `bun src/open.ts`. It takes the pane from `HERDR_PANE_ID` (herdr injects it for a key-bound action; verified in Task 0), falling back to `focused_pane_id` in `HERDR_PLUGIN_CONTEXT_JSON`, ensures the server is running, and opens the window. The agent session id is read later by the server from `herdr pane get`.

**Single window and toggle.** There is never more than one window, and the open key also closes it. `open.ts` asks the running server (`POST /api/toggle`): when a window is open, or was asked for in the last 6 s and is still starting, the server answers `close`, pushes `data: close` to the window's event stream (the window closes itself) and `open.ts` launches nothing; otherwise it answers `open` and `open.ts` launches the window. Each window has a random id, says `hello` once, `ping`s every 3 s and says `bye` on `pagehide`; the server forgets a window after 9 s of silence unless its event stream (opened with `win=<id>`) is still connected, and a `hello` from a new window tells every other window to close (the newest wins). A close is also remembered per window and returned as `close: true` in the answer to that window's next `ping` or `hello`, so a window whose stream was dropped still closes. A `hello` ends the opening state, the last `bye` clears it, and a `ping` or `hello` within 5 s after a `bye` is ignored. If the toggle gets no valid answer (an older server, a timeout) `open.ts` launches as before. `/health` reports `SERVER_API_VERSION`; when `open.ts` finds a running server with another version (or none) it stops it, waits up to 3 s, and starts a current one, so an upgrade does not wait for the idle shutdown.

**4.2 Local server (Bun + TypeScript, one process)**
- Listens on `127.0.0.1` on a preferred port (47631, or `SIDECR_PORT`), falling back to a free port only when that one is busy, with a random token required on every request.
- Singleton: a pid/port file in the plugin state directory; a second `open` reuses the running server.
- Endpoints (all under the token):
  - `GET /api/conversation?pane=<id>[&before=<exchange id>][&n=<count>]`: without `before`, the latest exchanges (n defaults to the `exchangesShown` setting: 3, 5 or 10, default 5); with `before`, the block of n turns that ends right before that exchange, oldest first (n defaults to the `loadBlock` setting: 5, 10 or 20, default 10). n is clamped to 1..50 (a turn is a prompt with the messages queued after it). The answer adds `hasMore` (older exchanges exist), `oldestId` (the `before` of the next older block) and `epoch` (changes when the transcript is indexed again, for example after it was replaced: ids from another epoch are stale) to the pane, machine and `exchanges` fields; every exchange has a stable `id` (the prompt row's uuid, else `@<byte offset>`). `activity` is computed for the latest exchanges only, never for a block. An invalid `before` or `n` is a 400, an unknown exchange a 404 `unknown-exchange`, both with `{error}`. See 5.5.
  - `GET /api/events?pane=<id>`: server-sent events. The stream sends a bare `data: changed` ping when the transcript size or the pane status changes (the window then refetches the conversation) and a final `data: gone` after 5 consecutive failed herdr probes. A settings change is pushed to every open stream as a named event, `event: settings` with the full settings as JSON data (a page that does not listen for it never sees it). A stream opened with `win=<id>` also gets `event: focus` (see 4.6): once when it connects, if the server knows where herdr's focus is, and then whenever it changes.
  - `POST /api/send`: message text and zero or more files.
  - `GET /api/file?path=<p>`: serves a preview of an image that appears in the conversation or was attached (see section 7).
  - `GET /api/image?pane=<id>&ex=<exchange id>&block=<u|a><n>`: the bytes of an image pasted into the terminal (base64 in the transcript; the window shows it as a `data:` URL), found by exchange id in the whole session (through the history index) and block, with the same headers as `/api/file`. It exists so the shell's lightbox window and the Media & links panel can load such an image by URL.
  - `GET /api/media?pane=<id>&kind=images|links[&cursor=<opaque>][&limit=<n>]`: the Media & links panel's lists, newest first, `limit` 1..100 (default 40). Answer `{ kind, items, next, progress, complete, total }`: `next` is the cursor of the next page (null at the very end; while the index is still growing it keeps a cursor so the window can ask again), `progress` 0..1 is how much of the transcript the media index covers. An image item is `{ exchangeId, i, kind: "block" | "path", src, thumb, at }` where `src` (and `thumb`, the same: there is no resizing) is the `/api/image` or `/api/file` URL the window would use; a link item is `{ url, host, title?, count, exchangeId, at }`, data only, opened through `/api/open`. A cursor from another epoch is a 410 `stale-cursor`. See 5.6.
  - `GET /api/settings`: `{ settings, schema: { groups, settings }, about: { version, stateDir } }`. The schema (`src/settings-schema.ts`: id, type, default, choices or range, label, group) is what the settings panel is rendered from. `PUT /api/settings` (JSON, a partial object of setting ids to values): each key is validated on its own; valid ones are saved, invalid values and unknown keys are listed in `rejected` and change nothing; the answer is `{ settings, rejected }` with the full result. Kept in `settings.json` in the state directory (temp file and rename, like `drafts.json`); a missing or corrupt file gives the defaults, unknown keys are dropped and an invalid value falls back to its default, never an error. Without a state directory the settings live in memory only.
  - `GET /api/panes`: the agent panes that run Claude (id, title, status, workspace label), for the switcher.
  - `POST /api/stop` (JSON `{ pane }`): sends one Esc to the pane, only while it is a Claude pane that is working (409 `not-working` otherwise); a second stop for the same pane within 1.5 s is answered `deduped` without sending.
  - `GET /api/draft?pane=<id>` and `PUT /api/draft` (JSON `{ pane, text }`): the unsent text of a pane, kept in `drafts.json` in the state directory (at most 50 panes, 20,000 characters each; longer is 413).
  - `POST /api/open` (JSON `{ pane, kind: "url" | "path" | "dir" | "reveal", target }`): hands a clicked link to the OS. A URL must be http(s); a path (`path`, and any other unknown kind) must be of an openable type (section 7) and one of the paths shown in the conversation or an attachment. `dir` opens a folder in the default file manager: the target must be absolute after `~/` expansion (a drive letter on Windows, a leading slash elsewhere), not a network share or device path (a leading `\\` or `//`, so `\\?\` and `\\.\` too), not carry an alternate data stream (a `:` past the drive letter) or a control character (NUL included), and be at most 4096 characters, else 400 `bad-path`; it must be one of the paths the conversation shows, or the folder that directly contains one of the files in that set (one level, never a root), compared like files (resolved, lower-cased on Windows, whole path), else 403 `forbidden`; it must exist (its real path, links followed, must not lead to a share), else 404 `not-found`, and be a directory; a regular file that was mentioned itself (an extensionless file such as `/etc/hosts` or `~/.bashrc`, which the window cannot tell from a folder) is shown in its folder instead: the opener is called with the real path and kind `reveal` and the answer is `{ ok: true, revealed: true }`; anything else that exists (a device, a socket, a file reached only as the parent of a file) is 404 `not-found` (415 `not-a-directory` is no longer answered). A folder allowed only as the parent of a file is refused (403) when its real path is a drive or filesystem root (a junction to `D:\`). The opener is called with the real path and kind `dir`. `reveal` shows a file in its folder: the same text rules and allow-list as a file, it must exist, but no type check, since the file is only pointed at (Windows `explorer.exe /select,<path>`, macOS `open -R <path>`, Linux `xdg-open <parent folder>`); it is the only way a script or an executable is ever handed to the OS, and it never runs it. On Windows the command line is written by hand and passed verbatim (`windowsVerbatimArguments`): `explorer.exe "<folder>"` and `explorer.exe /select,"<file>"`, the path always in double quotes with backslashes, never through a shell, as a GUI process (no hidden window; Explorer's exit code 1 is normal and ignored). Quoting is needed because Explorer's grammar uses the comma as a separator and Bun only quotes an argument that has a space, a tab or a quote; a double quote, a control character or a trailing dot or space in the path is refused (400 `bad-path`). On macOS a folder whose name has an extension, or that holds `Contents/Info.plist` (an application bundle, which `open` would run), is shown with `open -R`; `/` is opened as it is. On Windows a path ends without a backslash inside the quotes (`"C:\a\"` would read as `C:\a"`), a drive root is written without quotes (`explorer.exe D:\`) and a root cannot be revealed (400). The real path (after links are followed) is held to the same text rules as the request (control characters, network or device prefix, and on Windows a quote, a trailing dot or a space): 400 `bad-path`, never a failure of the opener.
  - `POST /api/window-bounds` (JSON `{ x, y, w, h }`): remembers the window placement in `window.json` in the state directory; `open` passes it to the browser on launch.
  - `POST /api/window` (JSON `{ id, event: "hello" | "ping" | "bye" }`) and `POST /api/toggle` (JSON `{ pane }`, answers `{ action: "open" | "close" }`): the window registry behind the single window and the toggle (see 4.1). The event stream also takes `win=<id>`, so the server can push `data: close` to that window.
  - static UI files, and for the shell's lightbox window `/lightbox.html` (a plain page) with its script `/lightbox.js` (built from `ui/lightbox.ts`), under the same cookie as everything else.
- Idle shutdown: the server exits when no window has been connected for a while.

**4.3 Window**
Edge, Chrome or Chromium (in that order) launched with `--app=<url>` and its own `--user-data-dir`, so the window has no browser chrome, remembers its size, and does not touch the user's profile. The UI is a small single page in plain TypeScript, no framework, bundled by Bun.

**4.4 In-window shortcuts and the switcher**
The window handles its own keys, so these need no herdr binding:
- `Ctrl+Shift+K`: opens a quick switcher listing the agent panes (from `herdr agent list`: pane title, workspace, agent status). Typing filters by name, Enter rebinds the window to that pane (it loads that pane's last two exchanges), Esc closes the switcher. This moves the one window between panes; it is not a dashboard of several.
- `Alt+S`: closes the window, the same key the user binds in herdr to open it (see 4.1: the open key is a toggle). The match is on the physical key with no other modifier, so AltGr and Alt+Shift+S are left alone.
- `Ctrl+Shift+J`: also closes the window and returns to the terminal.
- `Enter` sends, `Shift+Enter` adds a line, `Esc` closes the switcher or clears the attachment tray.

Since wave 4B every in-window shortcut is defined once in `ui/keys.ts` (id, keys, label, group, handler, whether it applies while typing); the key handler, the in-app cheat sheet (`Ctrl+/`, `?` outside a text field, the `?` chip in the composer, or the settings panel) and the tooltips all come from it. Additions: `Ctrl+K` (switcher), `Ctrl+,` (settings), `Alt+Up`/`Alt+Down` and `Alt+1..9` (another pane of the switcher's list), `Ctrl+End` (scroll to the bottom), `Ctrl+Shift+C` (copy the last answer as Markdown), `F` in the lightbox (fullscreen), Shift+click on a thumbnail (straight to fullscreen). `Enter` or `Ctrl+Enter` sends per the `sendKey` setting. Esc closes, in order, the lightbox, the switcher, the settings, the cheat sheet, the attachment tray and a timed notice; with none of them and an empty composer it closes the window.

**4.5 Native shell: settings and the lightbox window**
- The page applies the appearance settings through the Tauri window API, with no app command: `setEffects` / `clearEffects` and `setAlwaysOnTop` (capability `core:window:allow-set-effects`, `core:window:allow-set-always-on-top`). `open.ts` reads `settings.json` and starts the shell with `--no-topmost`, `--effect acrylic|mica|blur|none` and `--tint 0-255`, so the window opens with them.
- The lightbox window: the one app command `open_lightbox(srcs, index)`, reachable only through its app-manifest permission (`allow-open-lightbox` in `build.rs`, granted to the `main` window's loopback page). It refuses any caller but `main`, takes 1 to 64 same-origin image paths (`/api/file?...` or `/api/image?...`, no full URLs, no fragment) and loads `/lightbox.html?i=<n>&src=...` from the launch origin in a second window, label `lightbox`, covering the monitor the main window is on (black, topmost, no taskbar entry). A second call while it is open loads the new images in it. Its capability (`capabilities/lightbox.json`) allows only closing and destroying itself, loopback origin only, and it has the same navigation guard as the main window. When it closes the shell focuses the main window and sends it `sidecr:lightbox-closed`; when the main window goes, the lightbox goes too.

**4.6 Following the pane selected in herdr (wave 5)**
- Setting `followFocus`: `idle` (default), `auto` or `off`, label "Follow the pane selected in herdr", Behaviour group.
- Server (`src/focus.ts`): `herdr pane current` through `Herdr.currentPane()`, argv only, with `HERDR_PANE_ID` removed from the child's environment (herdr answers that command with the pane named by the variable, marked `focused: false`, when it is set; the server inherits it from the pane the plugin started in). An answer without a pane, or with `focused: false`, is an error. Polled every 700 ms only while a window is registered or has a connected stream and `followFocus` is not `off`; one read at a time (the next poll is scheduled when the previous one ends); `herdr pane current` is killed with its process tree after 3 s (`ExecOptions.timeoutMs`, used only by this call; sends and screen reads keep no limit), and the poller also gives up on any step after 4 s, both counted as failures; errors back off 1.4 s, 2.8 s, then 5 s, cut short by a window's `hello` or a new window stream; polling stops by itself when it is no longer needed and forgets what it saw, so the next start reports the focus again. `wake()` on a window's stream connecting, a `hello`/`ping`, and a settings change. The change key also carries whether a local Claude pane's transcript exists (looked up again every 3 s while it does not), so a new session's file turning up is pushed. `createServer(...).stop()` stops the poller with the server. A stream opened with `win=<id>&focus=only` carries close pushes, settings and focus events with no pane probes: a window whose pane is gone keeps one.
- Event `event: focus`, data `{ paneId, agent, isClaude, title, workspace, remote, transcript?, machine? }`, pushed to window streams when the focused pane id, or whether it is a Claude pane, changes. `workspace` is the label (the same cached workspace list as the header). `remote` is true when herdr names a machine other than this one, or when the cwd belongs to the other OS family (a POSIX path on Windows, a drive path elsewhere); `transcript` (local Claude panes only) says whether `findTranscript` found the session's file. `/api/conversation` for a pane whose transcript is missing and whose cwd is foreign answers `error: "other-machine"`.
- Window (`ui/follow.ts`, pure, wired in `ui/app.ts`): the first focus a window hears is only a starting point: it is remembered to tell repeats from changes, but no decision sees it until herdr reports a different pane (it keeps the pane it was opened on through sends, unpinning and mode changes). A Claude pane with `transcript: false` is ignored like a non-Claude pane. With the chip shown, a composer emptied by editing switches after 1 s without input (typing cancels the wait), a send switches at once. With attachments pending, the first chip press or `Alt+.` changes the chip to "Discard N attachments and switch" and the second switches. After `data: gone` the window reconnects a focus-only stream. Recalled text (ArrowUp) is saved as the draft. Shell-only shortcuts are not matched outside the shell. After a 150 ms debounce: off or pinned, nothing; not a Claude pane, nothing (no flicker); the pane shown, nothing; another machine's pane, an info notice "This agent runs on another machine; its conversation is not available here" (once per pane); a send in flight, wait and decide again when it ends; a pending attachment (any mode) or, in `idle`, a non-empty composer, the chip `herdr is on <name>: switch` under the header (click or `Alt+.`); otherwise switch through `setPane`, the switcher's own path, and flash the title area. A manual switch (switcher, `Alt+Up`/`Alt+Down`, `Alt+1..9`) pins the window while the mode is not `off`; the header pin button (Phosphor push-pin, filled when pinned, tooltip "Following herdr (Ctrl+Shift+L)" / "Pinned to <title> (Ctrl+Shift+L)") and `Ctrl+Shift+L` toggle it, unpinning catches up at once, `Alt+.` unpins and goes to herdr's pane. The pin is per window session, not saved. A pinned window shows the title in the accent. Turning the setting off forgets herdr's focus.
- Sending is unchanged: `/api/send` checks the pane id it is given with `getPane` (an unknown pane is a 502 from herdr's error) and `assertSendable` (not Claude: 409 `not-claude`), so the target is always the pane in the header and a pane that went away or stopped running Claude is refused.
- `Ctrl+Shift+T` (shell only) and a header button next to the gear toggle `alwaysOnTop` through the settings client, with an info notice "Always on top: on/off".

Chromium reserves some chords (for example `Ctrl+Shift+J` opens DevTools in a normal window). The page must intercept them with `preventDefault`; task 0 checks that this works in an `--app` window on Edge and Chrome.

## 5. Data flow

### 5.1 Finding the conversation
`herdr pane get <pane>` (or the plugin context) returns `agent`, `agent_session.value` (the session id) and `cwd`. The transcript is `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`, where `<encoded-cwd>` is the cwd with path separators and the drive colon turned into `-` (for example `C:\Users\alice\Documents\Notes\Garden` becomes `C--Users-alice-Documents-Notes-Garden`). If that file does not exist, the server searches every project directory for `<session-id>.jsonl`. If still absent, the window shows "transcript not found" and sending is disabled.

### 5.2 Parsing
The transcript is JSON Lines. Relevant line types: `user`, `assistant`, `system`, `attachment`. In `assistant` lines, `message.content` is an array of blocks (`text`, `thinking`, `tool_use`); in `user` lines it is a string or an array of blocks.

Rules:
- An *exchange* is one user prompt and everything Claude wrote until the next user prompt.
- Show the latest exchanges (a setting), and older ones in blocks on request (5.5).
- Show `text` blocks; show consecutive `tool_use` blocks as one expandable list ("3 tool calls") with a summary per call (the tool name and a one-line description of what it did); hide `thinking`.
- Skip meta lines (`isMeta`, `system`, `attachment` apart from `queued_command` below, `permission-mode`, `mode`, `last-prompt`, `bridge-session`).
- A message the user sends while Claude is working is not a `user` line when Claude Code records it: it is an `attachment` line whose `attachment.type` is `queued_command` and whose `attachment.prompt` is the text. Such a line starts a new exchange in order (marked `queued`, with the running turn's start time, so the elapsed clock and the token total carry on). Some queued messages are recorded again later as an ordinary `user` line with `promptSource: "queued"`; an exact repeat of the text within the next 50 lines is the same message and is shown once. `queue-operation` lines (enqueue, dequeue, remove) are ignored.
- Read the tail of the file first, never the whole transcript at once; older parts are indexed in chunks only when asked for (5.5).
- Detect links with a URL pattern, and local paths (absolute Windows, absolute POSIX, `~/`), and `@path` mentions; render them as clickable.
- A local path whose last segment has no file extension (a dot followed by 1 to 10 letters or digits, one of them a letter), or that ends in a separator, is a folder candidate (`Token.dir`): `C:\x\y`, `C:/x/y` (not after a word character or a slash, so `file:///C:/x` stays text), `/home/x/y`, `~/y`, with an optional trailing separator; a POSIX path needs two segments (`/api` is a word, `/api/users` a path), `~/` one. The window links it as a folder (folder icon, tooltip "Open folder", focusable, Enter or Space opens it) and posts `kind: "dir"`; whether it exists is only known to the server, whose 404 becomes the notice "That folder no longer exists" (an older server's 415 is still worded "That path is not a folder"), and a `revealed` answer (a plain file) the notice "That is a file, not a folder, so it is shown in its folder". A file link of a refused type is answered with `kind: "reveal"` after the 403 `type-not-openable`, and Shift+click on any file link does the same. Names are matched with Unicode letters, so `~/Documenti/Città` is one path. A path with spaces is linked only when a delimiter ends it (`tokenizeCode`, `tokenizeFenceBody`, `wholePathRange` in `src/tokenize.ts`): an inline code span (single or double backticks, paired left to right on a line), a quoted string (double, single, typographic quotes; a single quote opens after a non-letter and closes before a non-letter, so an apostrophe is not a quote; a quote's closer search stops at a backtick, so a quote never swallows a code span) or a line of a fenced code block, whose whole trimmed content is an absolute path (drive and `:\` or `:/` with one segment, `~/` with one, `/` with two): no empty segment, no segment starting or ending in white space, no colon past the drive letter (on any platform: an alternate data stream cannot reach the allow-list) and no backslash on POSIX, none of `` ` " < > | ? * ``, no control character and no Unicode format character (category Cf: bidi controls, zero-width characters, the soft hyphen, the BOM; the plain patterns let them through and drop the whole match, and so does one right after a match, because U+FEFF is white space to a regex and would otherwise cut a Windows name short; a name that holds one is not a path at all), no closing `.`, `,`, `;`, `:` or `!`, at most 4096 characters. Words after the path inside the delimiters count as part of it (`` `C:\a b and more` ``, a fenced `app.exe --help`): the delimiters say where it ends and nothing guesses; the link is dead when no such file exists. Every whole-line absolute path inside a fenced block is a link in the window (spaces or not). It is one token with nothing else in it; anything else in the span leaves the plain patterns to decide, and plain prose or a `path:` label is never guessed. The server's allow-list and the window share the same reading: `collectPaths` reads assistant text with `markdownPaths` (`ui/markdown.ts`), a walk over the same parse tree and the same rules the DOM builder follows, so fences (in quotes or list items, any indent), code spans split over two lines, links, headings and tables agree by construction, and a user's text, which the window shows as plain text, is read by `tokenize` on both sides; the equality is tested over many shapes with a fake DOM. A plain file open (`kind: "path"`) goes through `resolveOpen`, the text and real-path checks that folders and "show in folder" run (no control or formatting character, no stream, no network or device prefix, no double quote, no trailing dot or space), then the allow-list and the disk. Linear time: backtick runs are indexed once per line, quote closers are searched with a cache, a failed search is never repeated (tests: 200,000 characters of hostile input, 250 ms).
- Images that appear as image blocks, or as paths to image files, render as thumbnails.

### 5.5 History in blocks
`src/transcript/history.ts` keeps, per transcript file, the byte offset where each exchange begins, its id, whether it was queued and its timestamp: an LRU of 4 sessions, at most 20,000 exchanges each (beyond that the oldest are not offered). A new index reads the end of the file first (512 KB, widened only for a single longer row) and steps backwards one chunk (1 MB) at a time, with a yield between steps, only until it has the turns asked for; older parts are indexed when a block or an exchange id needs them. A row's role is decided while scanning, with the queued-twin state of the rows before it. The twin check looks back 50 rows, so every chunk (the tail window too) is scanned after 200 whole rows before it, however many bytes they take, parsing only rows that can touch the twin state; when such a row sits among the first 50 of those, the warm-up doubles (up to 12,800 rows or 32 MB), so the result equals a parse from the start of the file. When 200 rows span more than a chunk (long tool output), the step indexes them too, so the warm-up never costs more than what the step indexes. A block is then parsed from its byte range only, a chunk at a time with yields, reading only the start row and assistant rows (tool results are never materialised). Parsed closed exchanges are kept per session (at most 400, about 32 MB; a bigger one is returned but not kept), and the last exchange, which may still grow, is parsed on from where the previous request stopped, so a refresh reads only the appended bytes. When the 20,000-exchange limit stops the history, the last block says `truncated` and the window shows "Older history not indexed" instead of the beginning marker. A file first seen under 256 bytes has its first bytes completed as it grows, so a replacement is still noticed. The index remembers the scanned size and scans only appended bytes; a file that shrank or whose first 256 bytes changed is indexed again from the end under a new epoch. The window keys one DOM block per exchange id: a refresh updates or appends only the tail blocks that changed (block by block), older blocks are never rebuilt; scrolling within 240 px of the top prepends the next block with the first visible block held in place.

### 5.6 Media & links
The same index collects, per session, the images (pasted image blocks; image paths in user and assistant text, each path once at its newest mention) and the http(s) links (user and assistant text, and the tool summaries the window shows; deduplicated by the URL without its fragment and with a lower-case host, with the mention count, the first exchange and its time, and a few words of title: a Markdown link's text, else the words before it on the same line; sorted by the first mention, newest first, so a later mention never moves a link past the panel's cursor; counts refresh when the panel is opened again). The latest exchange is read fresh on each request since it may still grow; older exchanges are indexed backwards a chunk per step in the background after a few steps up front. At most 5,000 images and 5,000 links per session, the newest kept. An image path joins the session's allow-list when it enters that list (the newest 5,000); a path the cap never let in does not. The allow-list only grows within a session (bounded at 20,000 paths, by what the indexer handed out), so a path that later leaves the list stays allowed.

### 5.3 Live updates
As built, the server polls the transcript file size every 500 ms and the pane status through herdr every 2 seconds, and sends a `changed` ping over server-sent events when either differs; the window refetches the conversation on every ping. After 5 consecutive failed herdr probes the stream sends `gone` and closes. File watching was not needed.

### 5.4 Sending
1. The window posts text and files to `POST /api/send`.
2. The server saves each file under `<state>/attachments/YYYYMMDD-HHMMSS-<name>` and builds the message: the text, then one `@<absolute path>` per file.
3. The server checks the pane before sending. It refuses, with the message "a menu is open in the terminal", when `herdr pane get` reports the agent state `blocked` (permission and trust prompts), or when the last 20 non-empty lines of `herdr pane read` contain `Esc to cancel` (slash menus such as `/model` leave the state at `done`, as observed in task 0). Otherwise, if Claude is `working`, it still sends: Claude Code queues typed input while it works.
4. It delivers with `herdr pane send-text <pane> <message>` followed by an Enter key press (`herdr pane send-keys`, or `herdr pane run`). The exact delivery for multi-line text is decided by task 0 below.

## 6. Error handling

| Situation | Behaviour |
|---|---|
| Transcript not found | Window shows a clear message, composer disabled |
| Pane gone or session changed | Window shows "pane closed", composer disabled |
| herdr not reachable | Window shows the error from the CLI, no retry loop |
| Menu open (state `blocked` or `Esc to cancel` on screen) | Send refused with an explanatory message, text kept in the composer |
| Attachment too large (over 25 MB) or unreadable | Rejected before saving |
| Browser not found | `open` prints which browsers it looked for and exits non-zero |
| Server already running | Reused, no second instance |

## 7. Security

- Server binds to `127.0.0.1` only, never to a LAN address.
- Every request needs the random token that `open` puts in the window URL.
- The cookie is `SameSite=Strict`, and every non-GET request is also gated on `Sec-Fetch-Site`: one that is neither `same-origin` nor `none` (a page on another site) is refused with 403. A request with no such header (curl, tests) passes the gate and still needs the token and the Host check.
- The JSON endpoints (`/api/stop`, `/api/open`, `/api/draft` PUT, `/api/settings` PUT, `/api/window-bounds`, `/api/window`, `/api/toggle`) require `content-type: application/json` (415 otherwise), which a cross-site form cannot send without a preflight.
- Opening a file hands it to the OS default handler, which runs scripts, so what can be opened is an allow-list, not a denylist: only a short list of document types (images, pdf, md, txt, json, csv, log, docx, xlsx, pptx, html, htm) can be opened from a click. Scripts and executables (exe, bat, cmd, com, ps1, psm1, sh, msi, js, mjs, vbs, vbe, wsf, hta, jar, lnk, url, reg, scr, dll, appimage, desktop and anything else off the list) never open: they are only revealed in their folder. `html` and `htm` are on the list on purpose, because the user asked for it: opening a local HTML file hands it to the default app, the browser, which runs the page exactly as a double click in Explorer would. It is not the only script-capable type that opens: `svg` was already on the list before this change and runs script in a browser too; the list is unchanged. Both are bounded by the same gates as every file: the path must be one the server handed out for that pane's session (a file the conversation mentions), it must exist, and the last extension decides (`page.html.exe` is an executable). The OS opener is spawned without `windowsHide` (rundll32 would pass SW_HIDE on to the program that opens the file, which would then start with a hidden window); a test guards that. Only images shown in the conversation can be previewed.
- Folders (`kind: "dir"`) and "show in folder" (`kind: "reveal"`) have the same two gates as files, a text check and the allow-list below, and then the disk: network and device paths, streams, control characters and anything over 4096 characters are refused before anything is looked at; a folder is only opened when the conversation mentions it (or it holds a file the conversation shows), and a link or junction that leads to a share is refused. The file manager is started without a shell (`explorer.exe`, `xdg-open`, `open`), the path as a single argument on Linux and macOS and, on Windows, inside double quotes on a command line written by hand, because Explorer reads a comma as a separator; nothing inside the folder runs, an application bundle on macOS is only shown, and `reveal` only selects a file and never opens it. Two limits stay: resolving a link that points at a network share (`realpath`) can reach the share before the result is refused, as the existing file open does, and a local process that swaps a folder for a file between the check and the spawn (a race that needs write access to that folder) could make the file manager open the file.
- Everything the user reads is English, the webview's and the browser's own menus included: `--lang=en-US` goes to the Chromium app window (with `--disable-features=Translate`) and to WebView2 in the native shell (kept next to wry's default `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`, the same on every window of the shell; the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` environment variable that tests use for a debug port is added to them by WebView2). `test/english-only.test.ts` guards the strings of the code.
- The attachments directory is created with user-only permissions.
- `GET /api/file` and `POST /api/open` only accept paths that appear in an exchange the server has handed to the window for this session (the latest exchanges and every older block loaded), image paths that entered Media & links' list (its newest 5,000 images, as far as the panel's indexing has gone), or the attachments directory. This allow-list only grows within a session and is bounded by what the indexer handed out (at most 20,000 paths); a new session starts it empty. They do not serve arbitrary paths. `GET /api/image` only serves a png, jpeg, gif or webp image block of an exchange of the pane's session (never SVG), with `nosniff` and a `sandbox` CSP. `GET /api/media` has the same gates as the other endpoints plus a `Sec-Fetch-Site` check of its own, and returns links as data only.
- Nothing is sent to any external service.

## 8. Platform notes

- Windows: herdr's socket is a named pipe, so the server uses the `herdr` CLI (found through `HERDR_BIN_PATH`) rather than talking to the socket directly. Plugin commands must be valid Windows argv. Paths are normalised for display and for the `@path` mentions.
- Linux: same code path, POSIX paths.
- `bun` must be on the PATH that herdr's daemon sees. The plugin does not resolve its own runtime: a manifest is static argv and a shell shim would not work on Windows. Making `bun` visible is an explicit install step (README). A herdr server started with a bare PATH does not find it; the fix is to link `bun` into `~/.local/bin` and restart herdr from a login shell. Windows works as is (Task 0, probe 7).

## 10. Task 0: spike before any build

The whole project rests on delivery into a live Claude Code pane. Before writing the server, run a throwaway spike on a scratch pane and answer these with pass or fail:

1. Does `herdr pane send-text <pane> "line one\nline two"` arrive as two lines in Claude's input box, or does only the first line arrive? If it breaks, what delivers a multi-line message intact (bracketed paste through `send-keys`, a different key sequence, or sending one line at a time with Shift+Enter)?
2. Does `@C:\path\to\image.png` typed through `send-text` make Claude Code attach and read the image?
3. Does Enter after `send-text` submit the message, and does it behave the same on Windows and Linux?
4. Does the key binding to a plugin action deliver the focused pane id on herdr 0.9.3 (Windows) and 0.9.1 (Linux)? (Windows: yes, through `HERDR_PANE_ID` and the context JSON. Linux: to be checked in the install QA.)
5. Does a plugin with a Windows-valid argv start `bun` correctly from herdr's PATH on Windows?
6. Which direct chord reaches herdr from the user's real terminal on Windows (`ctrl+shift+j` first, then `ctrl+alt+j`), and does it still reach herdr while a Claude Code pane has focus? Test it with a no-op plugin action that logs its invocation.
7. In an Edge `--app` window, does a page `keydown` handler receive `Ctrl+Shift+J` and `Ctrl+Shift+K` with `preventDefault` working, or does the browser take them first? Same check on Chrome and, on Linux, Chromium.

Output of the spike: a short findings note and a recommendation. Spike code is throwaway and not kept. If 1 or 2 fail with no workaround, this design stops and we report.
